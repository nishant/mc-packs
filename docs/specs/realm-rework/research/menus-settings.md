Research only: nothing in `/home/user/mc-packs` was edited. Scripts used are next to this file

### 1.2 The menu the item opens [read]

- **Data.** `scripts/catalog.js` (generated by `tools/admin-catalog.mjs`: it loads each pack's `main.js` in Node with
  a stand-in for the Minecraft modules and records `registerCommand`/`registerEnum`): 181 commands in 64 packs, each
  `{ name, description, permission, params[] }` (`realm:admin` itself is skipped, `SKIP` at `admin-catalog.mjs:21`).
  `scripts/presets.js` (hand-written): `GROUPS` (`:29-89`, 6 groups, 18 sections, each a list of pack folders),
  `NAMES` (`:112-294`, a two-line label per command; `admin-catalog --check` fails when one is missing or wider than
  `LINE` = 168 font pixels, `:96`), `PARAMS` (`:313-367`), `CONFIRM` (`:373-388`), `SETUP` (`:401-419`, 17 steps),
  `SIZE_OPTIONS` (`:428-444`, 15 options).
- **Which commands show.** `available(player)` (`main.js:109-113`): permission rank <= the player's
  `commandPermissionLevel`, and the pack answered `realm:help_ping` (`installed()`, `:93-106`: waits `answerTicks`
  = 10 ticks, cached 1200 ticks; nobody answered = show everything).
- **Home** (`mainMenu`, `:529-549`), one `ActionFormData`: `My Preferences` (runs `/realm:prefs`), operators
  `Realm Settings` (runs `/realm:config`), `Recent (n)`, `Search`, the label `What do you want to do?`, one button
  per group, `Other` (packs no group lists), operators `Operator Tools`. Body: `119 commands you can use from 61
  packs. Each page scrolls; the second line of a button says what it does.` (`:547`).
- **Group page** (`groupPage`, `:552-560`): every command of the group's packs on one scrolling page, a bold label
  per section, ordered by pack, then player commands before operator ones, then names without `_` first
  (`grouped`, `:505-526`). `Back` is the last button (`list`, `:169-193`).
- **Running a command** (`openCommand`, `:374-417`): no parameters = run at once; otherwise a `ModalFormData`
  built by `paramForm` (`:284-366`): Enum = dropdown (optional ones start on `(leave out)`), a player = dropdown of
  online names plus a text box for String parameters, Boolean = toggle, numbers = slider when `PARAMS` says so,
  else a text box (positions prefilled), anything else = text box (an ItemType starts with the held item).
  Destructive commands and anything aimed at `@a` ask `Are you sure?` (`needsConfirm`, `presets.js:388`).
  `exec` (`:240-262`) re-checks the permission, calls `player.runCommand(line)`, says
  `[Realm Configuration] Ran /realm:...` or `... didn't run: the command refused. Check the options, or type it to
  see its reason` (the game does not hand the reason to the script), and stores it in Recent.
- **Coming back** (`resume`, `:152-163`): waits `answerTicks * 2 + 5` = 25 ticks, then shows the page again. If the
  command opened its own menu the re-show gets `UserBusy` and gives up at once (`show`, `:133`), so after a pack
  menu closes the player is back in the world, not in the star's menu.
- **Search** (`:563-586`): a one-box modal, then every command whose name, description, pack or label holds every
  word. An empty search lists everything. **Recent** (`:592-619`): the last `recentSize` (8) commands run from
  this menu, with their arguments, in the player property `admin:recent`.
- **Operators** (`opsPage`, `:626-657`): `Set up this world` (`setup.js:290` `wizard`), `Server size`
  (`setup.js:484`), 12 quick actions (`actions.js`), `Pack diagnostics`, the 17-step setup checklist with done
  marks, then admin_bp's own commands. Operator entries are dark red (`OP_COLOR`, `presets.js:102`).
- **Forms that cannot open.** `show()` (`:125-141`): on `FormCancelationReason.UserBusy` it waits 20 ticks and
  retries, 20 times (20 s), then says `Couldn't open the menu. Close chat or your inventory and try again.` A page
  that outlives its player (left, died, respawned) stops quietly (`lifecycle.js`, `alive()`); the setup wizard
  waits up to 2400 ticks for a pack's menu to close (`setup.js:23, 255-280`).

### 1.3 `/realm:help` (`packs/help_bp`) [read]

- `scripts/catalog.js` (3,386 lines) is generated by `tools/help-catalog.mjs` from `docs/PACKS.md`: per pack
  `{ folder, topic, name, summary, steps[{text, ops}], commands[{usage, ops, who, text}] }`. A step is an operator
  step when it starts with `**Operators` (`help-catalog.mjs:66`); a command is an operator command when its Who
  cell matches `/^ops\b/i` (`:79`; see bug B1).
- `openHelp` (`main.js:122-155`): `installed()` (`:31-41`) pings `realm:help_ping` and waits `answerTicks` (10),
  then one `ActionFormData`: `All commands` and one button per installed pack, **in docs order** (Realm Settings,
  Realm Configuration, Welcome Message, Low Durability Warning, AFK + Smart Sleep, Stats ... Story Questlines is
  33rd), second line = the pack's commands (`/realm:stash | /realm:sort | +4 more`, `buttonLine`, `:78-83`).
- A pack page (`packPage`, `:100-116`): summary, `How to use` steps, `Commands`, then `Back` and `Close`, all as
  labels on one form. `All commands` (`:86-97`) is every command of every pack on one form (about 45,000
  characters of text). `/realm:help <topic>` jumps to a page; `realm:help_topic` is an enum of 66 folder names.
- **No search.** `UserBusy`: 20 tries, 20 ticks apart, then `Couldn't open the help. ...` (`:52-61`).
- **`realm:help_ping` protocol**: anyone sends `realm:help_ping` (empty message); every behavior pack answers
  `realm:help_pong` with its folder name as the whole message (`help-catalog.mjs:125-132` fails the check when a
  pack does not). Users: help_bp, admin_bp (`main.js:83-106`), welcome_bp (`main.js:110-137`), news_bp (tips).
  One ping wakes 67 native listeners and gets 66 pongs, each of which wakes 67 listeners again: about 4,500
  dispatches per ping, each a `Map` lookup in `script-events.js` unless the pack subscribed to that id.

### 1.4 Settings (`packs/settings_bp`, `tools/settings-shared.js`) [read]

- **Declaring.** Each pack's `scripts/settings.js` sets `PACK`, `PREFIX`, `TITLE`, `BASE` (its `config.js`
  object) and `OPTIONS`, then calls `createSettings` from `settings-core.js` (a byte copy of
  `tools/settings-shared.js`, written by `tools/sync-settings.mjs`; stored once in the bundle). An `Option`
  (`settings-shared.js:15-39`): `key`, `type` (bool, int, float, enum, text), `scope` (`world` or `player`),
  `label`, `help`, `min`/`max`/`step`, `choices`/`names`, `invert`, `restart`; player options also `base` (the
  world option a player starts with) or `default`, `prop` (its own dynamic property instead of `<PREFIX>:pref`),
  `sticky`, `lock` (world values that make it do nothing) and `locked(player)`.
- **Storage.** World: `<PREFIX>:cfg`, JSON of only what differs from `config.js` (`set`, `:145-161`). Player:
  `<PREFIX>:pref` JSON on the player, or the option's `prop` (`setFor`, `:210-225`); a value equal to the realm's
  is deleted unless `sticky`, so the player follows later realm changes.
- **Protocol** (`:356-371`): `realm:cfg_ping {id, player?}` -> every pack answers `realm:cfg_schema {id, pack,
  title, part, parts, options}` split under 2048 UTF-8 bytes (`answer`, `:321-333`); `realm:cfg_set {id, pack, key,
  value, player?}` -> `realm:cfg_ack`; `realm:cfg_reset {id, pack}`. `describe()` (`:277-298`) always sends the
  world options too, also for `/realm:prefs`.
- **`/realm:prefs`** (`settings_bp/main.js:503-549`): `collect()` (`:48-77`) waits `answerTicks` (10), once more
  if a multi-part answer is incomplete, then builds **one** `ModalFormData` with a bold gold label per pack
  (alphabetical by title) and one control per player option; a locked option is a gray line. `Save` sends only the
  changed controls, then a summary dialog. Closing with X saves nothing and says so in chat (`:538-540`).
- **`/realm:config`** (`:324-351`): `All settings` (pages of at most 100 lines, `paginate`, `:392-409`), one
  button per pack, `Reset a pack to defaults`. An item renamed `Realm Settings` on an anvil opens it (`:569-577`).
- Two packs draw their own copy of their options: Easy Building (`build_bp/scripts/settings.js:2`: "shares the same
  eb:* dynamic properties used by Effortless Building's in-game settings") and Stats (`stats_bp/main.js:602-605,
  624`: `My ticker settings` lists "the same ones as in /realm:prefs").

### 1.5 What a new or returning player is told (`packs/welcome_bp`, `news_bp`) [read]

- 40 ticks after joining (`welcome_bp/main.js:335-341`, `DEFAULTS.delayTicks`) a popup with three sections
  (`defaultSections`, `:168-188`; text in `config.js:42-80`): **The World** (greeting, the story hook, `Tap Old
  Tobin or Mara in town to begin`), **What You Can Do** (up to 13 lines, each naming a slash command:
  `/realm:quests`, `/realm:expedition`, `/realm:bounty`, `/realm:town`, `/realm:skills`, `/realm:crowns`,
  `/realm:claim`, `/realm:calendar`, `/realm:party`, `/realm:mail`, `/realm:map`, `/realm:stats`,
  `/realm:journal`), **Where To Go Next** (`/realm:help`, `/realm:prefs`, `/realm:saga`, and `Operators:
  /realm:welcome_edit changes this message.`).
- `showOnce` is `false` by default (`config.js:26`): the popup comes on every join until the player turns off

  the popup. **The welcome never mentions the item**, and neither does any of the 9 chat tips
  (`news_bp/scripts/config.js:18-28`, one every 20 minutes): all teach typed commands.
- A returning player: the popup again, the news popup once per release 100 ticks in (`news_bp/config.js`,
  `delayTicks`), `Welcome back! You were away ...` after 12 hours, the unread-letters notice, the daily forecast.

## 3. Why people are not using the menu

Ranked by how much each one costs a player. All [read] unless marked.

1. **It is a list of commands, not of things to do.** The item is named `Realm Configuration`, its lore promises
   "every realm command you can use", the home screen's body counts them ("119 commands you can use from 61
   packs"), and the first three buttons are `My Preferences`, `Recent (0)` and `Search`. A new player sees nothing
   about the story, travel, quests or mail on the first screen. Operators carry the same item, so it reads as an
   admin tool.
2. **The groups follow the packs, so things sit where their code lives, not where a player looks.** Death Point is
   under `Items & Building > Inventory and chests`. Bounties are under `Friends, Crowns & Fun > Crowns and games`.
   Waystones are under `Towns & Townsfolk > Townsfolk and travelers`. Community Goals and the fish log are under
   `World & Events > Events and news`. Realm Help and Sit Down are under `My Screen & Toggles`. Skills is the 19th
   button of `Friends, Crowns & Fun`.
3. **Every page scrolls, a lot.** 14 to 24 buttons a page for a player (26 to 35 for an operator), on a phone that
   shows about 6. Half of the six groups are themselves below the fold of the home screen.
4. **Each pack shows up 2 to 13 times.** A pack's menu command and each of its sub-commands are separate buttons
   (`Party Menu`, `Accept Party Invite`, `Party Chat`, `Invite to Party`, `Leave Party`; 13 Easy Building buttons;
   `Weather Almanac` and `Weather Forecast`). Of the 120 player commands, 58 only repeat what another button's own
   menu already offers (appendix A lists each with the reason).
5. **Nothing is contextual.** No badge for unread mail, no "you died over there", no "a festival is on", no next
   story step. The menu looks the same every time, so there is no reason to open it "just to check".
6. **No favorites, and Recent starts empty.** Recent only fills from commands run through this menu and is one more
   screen away; the things a player does ten times a session (quick stack, sort, find) always cost the full path.
7. **The menu does not come back.** After a pack's own menu closes, the player is back in the world
   (`resume`/`show`, section 1.2) and has to use the item and navigate again for the next thing.
8. **Toggles open forms.** `Toggle Minimap` asks for `Action` and `Radius` in text boxes before it runs; `Realm
   Help` asks for a `Feature` in a free text box.
9. **Nobody is told to use it.** The welcome popup and the chat tips teach 16 typed `/realm:` commands and never
   mention the item; the one chat line about it arrives behind the welcome popup. Typing `/realm:...` on a phone or
   a console is the hard way, so the features look hard.
10. **The item competes for a slot and may not be in the hotbar.** It goes to the first free slot; a full hotbar
    puts it in the inventory, where using it takes: open inventory, move it, close, select, use.
11. **[suspected] The touch gesture is weak.** A nether star has no use action, so on a phone "use" is a long
    press, which aimed at a block starts mining instead. A real-client check is needed; section 6.6 has a fix (a
    custom item with an interact button) if it confirms.
12. **`/realm:help` is a second, separate front door** with a different order (docs order, 67 buttons, meta packs
    first) and no way from a help page to the thing it explains.
13. **`/realm:prefs` is one form of 126 rows**, alphabetical by pack name. To switch off rain sounds a player
    scrolls past 22 Easy Building rows and 15 stats ticker rows, then back down to `Save`.

`Option`, passed through `describe()` into `realm:cfg_schema`:

```js
/**
 * @property {"screen" | "alerts" | "play" | "effects" | "look" | "own"} [page] the Settings page that shows it
 *   ("own": the pack's own menu edits it; shared forms other than All My Preferences leave it out)
 * @property {"advanced" | "hidden"} [tier] advanced: behind Show advanced. hidden: never drawn, still read, set
 *   and reset (world options only)
 * @property {{ hud?: unknown[], notify?: unknown[], layout?: unknown[] }} [preset] the STORED value each level
 *   gives it: hud [Minimal, Normal, Everything], notify [Quiet, Normal, Chatty], layout [now, right, left, hotbar]
 */
{ key: "off", type: "bool", scope: "player", invert: true, label: "Elytra HUD while gliding",
  page: "screen", preset: { hud: [true, false, false] }, lock: [["enabled", false]] },
```

- Applying a preset is settings_bp sending the same `realm:cfg_set {id, pack, key, value, player}` it sends today,
  one per option whose value differs, then the existing summary (`save()`/`report()`, `settings_bp/main.js:270-311`).
  This is exactly how Server size already works (`presets.js` `SIZE_OPTIONS`, `setup.js:484-570`).
- Nothing new is stored. The level a picker shows is computed from the values in the schema
  (`levelOf(options, kind)`: the level every unlocked governed option matches, else `Custom`). Keys, properties
  (`<PREFIX>:pref`, `durability:off`, `eb:*`) and `setFor`'s "equal to the realm's value clears it" rule are
  unchanged, so a player who never opens Quick Setup keeps exactly what they have, and one who does can still
  change any single switch afterwards.
- Locked options (`locked` in the schema) are skipped and named in the summary. `sticky` options keep working: a
  preset writes through `setFor`.
- For operators the same three pickers, titled `New players start with`, write each governed option's `base`
  world key (`realm:cfg_set` without `player`), which replaces 36 "realm default" options with 3 pickers.
- `tier: "hidden"` must hide, not delete: `get()` only honors a saved override while the option is in `OPTIONS`
  (`settings-shared.js:127-139`), so deleting a D option would silently revert worlds that changed it.

### 6.2 The tree as curated data: yes, in admin_bp

The generated catalog stays the source of **what exists** (commands, permissions, parameters). `menu.js` is the
curated **where it goes**. The generator cannot guess tasks, and a hand-written tree that can drift is exactly
what `check-menu` prevents: a new command fails `npm run check` until someone places it or hides it with a reason.

```js
// packs/admin_bp/scripts/menu.js
/**
 * @typedef {object} Entry
 * @property {string} [cmd] a registered command: runs it (its options form first, as today)
 * @property {string} [screen] or: opens that screen (label and hint come from the screen)
 * @property {"alert" | "pins" | "search" | "recent" | "topics" | "az" | "presets" | "size" | "actions"
 *   | `prefs:${string}`} [builtin] or: something main.js draws itself
 * @property {string} [label] default NAMES[cmd][0]
 * @property {string} [hint] default NAMES[cmd][1]
 * @property {string} [key] the id its pack answers realm:menu_pong with (badge, hint, alert, show)
 * @property {true} [when] shown only while its pack's pong includes `key`
 * @property {true} [stay] reopen this screen when the command's own menu closes
 */
/** @typedef {{ title: string, hint: string, ops?: true, sections: { title?: string, items: Entry[] }[] }} Screen */
```

### 6.3 How other packs contribute: `realm:menu_ping` / `realm:menu_pong`

Same shape as `realm:help_ping`, with a request id and JSON. No pack imports another; a pack that is not there
simply does not answer and its entries keep their static text.

| | |
|---|---|
| Request | `realm:menu_ping` `{ id, player, v: 1 }`, sent by admin_bp once when a player opens the menu. `id` = `<tick base 36>.<counter>` like settings_bp's `newId()` |
| Answer | `realm:menu_pong` `{ id, pack, items: [{ k, t?, h?, n?, a?, c?, hide? }] }`, one message per contributing pack, always sent (an empty `items` too), under 2048 UTF-8 bytes |
| `k` | The entry's `key` in `menu.js` (at most 24 characters). admin_bp ignores a key whose entry's command does not belong to the answering pack (checked against the catalog's `folder`), so no pack can rewrite another's button |
| `t`, `h` | Line 1 and line 2 overrides, plain ASCII, at most 40 characters each; admin_bp strips `§` codes and cuts to `LINE` with the existing `fit()` |
| `n` | A count 0 to 999: line 1 gets ` (n)` |
| `a`, `c` | `a` 1 to 100 makes it an alert candidate (4.4); `c` is the command the alert runs, which must be a registered command of the same pack that the player may run (default: the entry's command) |
| `hide` | `1` hides a normal entry (`My Land` while claims are disabled). An entry with `when` shows only if its key is in the pong |
| Limits | 8 items a pack; admin_bp drops the rest. Unknown fields are ignored (`v` lets the shape grow) |
| Waiting | admin_bp keeps the set of packs that have ever answered since the world loaded (`contributors`). It waits until all of them answered, at most `menuTicks` (new config, default 4 ticks; the first open of a session waits the full 4). Then it draws with whatever arrived; missing answers = static text |
| Cache | A player's pongs are reused for 40 ticks, so moving between screens does not ask again; running a command asks again |
| Cost | Nothing per tick: no interval, no listener work until a ping. Per open: 1 ping + about 15 pongs, each waking the 67 native listeners (a `Map` lookup that returns at once in the packs that do not subscribe): about 1,100 dispatches, the same order as one `/realm:help` (about 4,500, section 1.3) and far below `/realm:prefs` (bug B6). Each contributor reads state it already holds in memory |

The helper every contributor copies (factory, no module state besides the callback it is given):

```js
// tools/menu-shared.js -> packs/<pack>/scripts/menu-items.js
/** @param {{ PACK: string, onScriptEvent: Function, items: (player: Player) => MenuItem[] }} args */
export function createMenuItems({ PACK, onScriptEvent, items }) {
  onScriptEvent("realm:menu_ping", ({ message }) => {
    let req; try { req = JSON.parse(message); } catch { return; }
    if (!req || typeof req.id !== "string" || typeof req.player !== "string") return;
    let list = [];
    try { const p = world.getEntity(req.player); if (p instanceof Player) list = items(p).slice(0, 8); } catch (e) { console.warn(`[${PACK}] menu: ${e}`); }
    system.sendScriptEvent("realm:menu_pong", clamp({ id: req.id, pack: PACK, items: list })); // under 2048 bytes
  });
}
// mail_bp/scripts/main.js
createMenuItems({ PACK: "mail_bp", onScriptEvent, items: (p) => {
  const n = unreadOf(p);
  return [{ k: "mail", n, h: n ? `${n} unread` : undefined, ...(n ? { a: 70, t: `${n} New Letter${n === 1 ? "" : "s"}` } : {}) }];
} });
```

## 9. Risks

1. **The saga text on the first button depends on Story Questlines answering in 4 ticks.** If script events take
   longer on the Realm than on BDS, the first screen shows static text; that is safe but loses the best part.
   Measure the round trip on BDS first (`menuTicks` is a setting for this reason).
2. **Hidden is not gone, but it will feel gone to anyone used to a button.** 58 player commands leave the tree.
   A to Z, Search and pins cover it; say so in the news entry.
3. **Presets overwrite individual choices** when a player picks a level. The summary dialog already lists every
   change old -> new; `Custom` protects a hand-tuned setup from an accidental change only if the form opens on
   `Custom` (it does: the picker shows the computed level).
4. **`tier: "hidden"` versus deleting.** Deleting a D option reverts saved values (5.1). Hide only.
5. **Settings core change touches all 66 copies** (`sync-settings`), so every behavior pack's version goes up in
   one release, and `diag.js` with it. Ship it alone.
6. **The pack menus the tree relies on** must really contain their hidden sub-commands. Read for Party, Crowns,
   Expeditions and Fishing; taken from the command descriptions for the rest (`"a menu of what you can do (...;
   operators: ...)"`). Check each of the 58 `HIDDEN` reasons while building; `check-menu` cannot.
7. **Touch input** (3, item 11) is unverified; if it is the real blocker, the tree alone will not fix usage.
8. **Renaming the pack** changes its docs heading, so the help topic stays `admin` (the folder) but every link to
   `#realm-configuration--admin_bp` on the site and in `PACKS.md` (many) must change with it.
9. **An operator's Recent** holds lines with labels from today's `NAMES`; they keep working (the command line is
   what runs) but show old titles until rerun.
