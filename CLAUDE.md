# mc-packs

Minecraft Bedrock packs for a Realm. Each folder in `packs/` is a self-contained pack: behavior packs `*_bp` (`manifest.json`, `scripts/main.js`, `scripts/config.js`) and seven resource packs. `rain_rp`'s textures, fogs, client biomes, sounds and sound definitions are generated by `tools/gen-rain/` (`npm run gen:rain`; its particles and manifest are hand-written). `sky_rp` is generated entirely, manifest included, by `tools/gen-sky/` (`npm run gen:sky`). `translucent_rp` is generated (all but `manifest.json`) by `tools/gen-translucent/` (`npm run gen:translucent`). `hud_rp` (Side HUD) is one hand-written JSON UI file whose vanilla title frames are copied from Mojang's `hud_screen.json`, plus the Minimap's icon font `font/glyph_F3.png` and the pack icon, generated with `packs/map_bp/scripts/glyphs.js` by `tools/gen-glyphs/` (`npm run gen:glyphs`). `platypus_rp`'s model, skins and both platypus pack icons are generated by `tools/gen-platypus/` (`npm run gen:platypus`; its client entity, render controller, animations, lang and manifest are hand-written). `build_rp`'s textures and pack icon are generated by `tools/gen-build/` (`npm run gen:build`; its particles and manifest are hand-written). `silly_rp`'s sounds, particles and texture are generated by `tools/gen-silly/` (`npm run gen:silly`; its manifest is hand-written). Never hand-edit generated files.

**Before big or multi-pack work, read `docs/WORKING.md`**: the order of the finishing steps, how subagents and reviewers split the work, known API quirks, and how to keep a session cheap (read `docs/PACKS.md`, 1 MB, one `## ` section at a time; never open generated catalogs), plus the recurring bug checklist (C1-C29) to apply to every pack you touch. Server owners outside this Realm start at `docs/SERVER_SETUP.md`: keep it current when install steps, requirements, Server size or performance change.

## Rules

- **Ship every change; don't ask.** The owner has standing approval: never ask whether to open a PR, merge, publish or deploy. Unless the request says otherwise, a change is done only when:
  1. `npm run check` and `npm run build` pass, and the change is committed with its docs, pushed, PR'd to the default branch **`master`** and merged by you with a merge commit (merge the default branch in first if it moved).
  2. The release notes are in `release/notes.json` in the same PR: `notes` for the Realm Bundle (and Realm Resources unless `resourceNotes` is given), `packNotes.<folder>` = `{ "version": "<new header.version>", "notes": "…" }` for every pack whose version went up (`npm run check` enforces it). After the merge, the `release` workflow (`.github/workflows/release.yml`, once `check` is green on `master`) publishes, regenerates the realm page, merges the hosting PR (that's the deploy) and runs check-live: wait for that run and read its job summary. **Fallback** when its summary says "Release skipped: no HOSTING_TOKEN" or the run failed: in `nishant/hosting` (cloned next to this repo; attach it to a cloud session if it isn't there), `cd minecraft`: `node tools/publish-packs.mjs --from <this repo> --notes "…" --pack-notes <folder>="…"` for every pack whose version went up (`--notes` whenever anything in the Realm Bundle changed), `node tools/pack-docs.mjs --from <this repo>` (and `--check`), `node tools/check-site.mjs realm` (only the realm page changes in a pack publish; a full run is for site changes), then a PR to `master` that you merge (that's the deploy). The two paths don't conflict: a version is published once. Docs-only changes skip publishing but still regenerate the realm page.
  3. check-live passes (the release run's last step, or `node tools/check-live.mjs` in hosting on the fallback): it waits for the deploy and checks the live pages, every pack's latest `.mcpack` and the realm page in Chromium. Never fetch a new file's URL before that: Cloudflare caches a 404.
  4. The owner gets a short summary with numbers (and the listening clips or pictures when they changed). It is assumed the Realm Bundle and Realm Resources get uploaded to the Realm after each release; the owner does it. End the summary with one line: site up to date and the actual Realm Bundle and Realm Resources versions live at https://mc.nish.software/realm/ after check-live passes (the release run's summary names both).
- **Review before the first publish**, not after: a publish followed by a fix pass doubles the work. With the release workflow the first publish is the merge, so review before merging.
- **Docs stay current.** Any change to a pack's behavior, commands, config options or saved data updates `docs/PACKS.md` (and the `README.md` pack table if the summary or commands change) **in the same commit**. `npm run check` only checks coverage (every pack, registered command and `config.js` option), so keep descriptions and defaults accurate yourself. Write Commands rows for players: give the default, with the option name in parentheses (`default 64, \`defaultRadius\``).
- **Generated catalogs, regenerated last** (after every doc edit; `npm run check` fails until you do): the in-game `/realm:help` text (`packs/help_bp/scripts/catalog.js`) comes from each pack's summary, `### How to use` and Commands table: `node tools/help-catalog.mjs` (it bumps `help_bp`). The Realm Configuration menu (`packs/admin_bp/scripts/catalog.js`) lists every registered command: after adding or changing a command or its parameters, `node tools/admin-catalog.mjs` and bump `admin_bp`. Nicer labels, ranges and setup checklist entries go in `admin_bp/scripts/presets.js`.
- **The docs are also the players' docs.** `docs/PACKS.md` is published on https://mc.nish.software/realm/ (by `minecraft/tools/pack-docs.mjs` in `nishant/hosting`; see "Publishing to mc.nish.software" in PACKS.md). Every pack section needs a `### How to use` (numbered steps, operators last). Write plain American English (color, gray, behavior, traveled, canceled), but quote in-game text and ids exactly as the code has them, in backticks.
- **New pack:** add `packs/<folder>/` (its `main.js` must answer `/realm:help`: copy another pack's `onScriptEvent("realm:help_ping", ...)` responder with its own folder name; run `node tools/sync-events.mjs` to add `scripts/script-events.js`, then `node tools/sync-diag.mjs` to add `scripts/diag.js` and its first import), a `## <Name> — \`<folder>\`` section in `docs/PACKS.md` (same layout as the others: what players see, Commands, Configuration, Saved data), a row in the README table, and a mention in "How the packs work together" if it interacts with other packs.
- **Game text is plain ASCII** (plus `§` codes): Bedrock draws `…`, `–`, `•`, `·` or an emoji in a smaller fallback font. One exception, approved by the owner: the Minimap's icons are Private Use Area characters (page U+F300-U+F3FF, drawn by Side HUD's glyph font), and they live only in the generated `packs/map_bp/scripts/glyphs.js` and go only into the map's HUD strings (compass strip, radar), never chat, forms or story text; `check-ascii` enforces the file. Settings are named for what they do with an Enabled/Disabled switch (`invert` for options stored as `off`); never "Turn off ...". **Never use a form's `.header()`:** Bedrock draws it in a huge font that wraps a pack name over two lines; a section title is `.label("§l§6Title")` (bold gold, normal size). `check-ascii` fails on `.header(`.
- **Stable APIs only:** `@minecraft/server` 2.1.0 / `@minecraft/server-ui` 2.0.0, no beta modules or experiments, because the packs run on a Realm. Check game ids against `@minecraft/vanilla-data` (see the quirks in `docs/WORKING.md`).
- **Every behavior pack's `scripts/main.js` imports `./diag.js` first** (`import "./diag.js";`, before any other import): the diagnostics protocol behind `/realm:diag` (script time per pack, saved data, forgetting one pack's data) wraps what the pack registers after it. Never edit a pack's `diag.js`: it is `tools/diag-shared.js` with the pack's folder, name and version filled in by `node tools/sync-diag.mjs`.
- **Packs stay independent:** no imports between packs. Coordinate through tags, scoreboards or script events (e.g. the AFK pack's `afk` tag that Stats reads). Never subscribe to `scriptEventReceive` directly: use `onScriptEvent` / `offScriptEvent` from the pack's `script-events.js` (one native listener per pack, checked by `node tools/sync-events.mjs --check`). Dynamic property keys use the pack's own prefix (`news:…`): the bundle keeps every pack's saved data in one store, so never call `world.clearDynamicProperties()`. Script event ids are `realm:…` and every message stays under 2048 characters (split long lists into parts, like the safe zones protocol). Before every `setActionBar`, send `realm:actionbar` `{ player, ticks, from }` (a steady line's own redraw adds its rank, `steady`); a line that redraws every second also listens and waits while someone else's request lasts (the action bar protocol in "How the packs work together").
- **Commands all use the `realm:` namespace**, named `realm:<pack>` or `realm:<pack>_<action>`. A bundle is one add-on and Bedrock allows one command namespace per add-on: a second throws `NamespaceMismatch` and those commands never register.
- **Bundles:** the Realm runs two packs, `npm run bundle -- --all` (Realm Bundle, every behavior pack) and `npm run bundle -- --resources` (Realm Resources, every resource pack), minus those in `tools/standalone.json` (empty). A pack can't mix the two kinds, so two is the minimum; keep it that way. Every pack is still published on its own too. Resource packs are merged only at bundle time, in `dist/`: never merge them on disk (each generator deletes files it didn't make). Standalone and resource packs still follow every rule here so they can join the bundle later.
- **Pictures and sound clips** go in `docs/media/` and a pack's `### See and hear it` subsection (`![caption](media/…)`, `[label](media/….mp3)`, and `![Before](media/…) ![After](media/…) caption` on one line for a before/after pair). The rain packs' are generated (`node tools/gen-rain/renders.mjs`, `node tools/gen-rain/sounds.mjs --audition docs/media/rain`): rerun them when the rain texture, fogs or sounds change. So is Silly Enchants' cheer (`node tools/gen-silly/gen.mjs --audition docs/media/silly`): rerun it when the cheer changes. The Minimap's render (`docs/media/map/`) comes from `npm run gen:glyphs`. Label renders as renders, never as screenshots.
- **Realm News writes itself:** every shipped change that players notice adds a short entry at the top of `docs/NEWS.md` (for players, plain ASCII). `npm run bundle` runs `node tools/gen-news.mjs`, which puts the newest entry in `news_bp`. Never ask the owner to type news in game.
- **Test on a real server:** `tools/test-bds/` runs the packs on a Bedrock Dedicated Server with simulated players (see its README). Use it for anything that touches game behavior; locally, run the scenarios you are iterating on and let CI run the rest. `--bundle` runs the built Realm Bundle as one script context; CI smoke-tests that context on every PR.
- **Vanilla entity overrides:** `translucent_bp/entities/player.json` and `dolphin_bp/entities/dolphin.json` are copies of the vanilla behavior files plus our additions; only one pack may define each entity. After a Minecraft update, re-copy them from the newest vanilla files (Mojang's `bedrock-samples` repo, `behavior_pack/entities/`; BDS 1.26 packs its vanilla files into an archive) and re-apply the additions.
- **Version bumps:** increase `header.version` in a pack's `manifest.json` whenever its contents change (`sky_rp`: in `tools/gen-sky/gen.mjs`; `help_bp` and `news_bp` are bumped by their generators), then run `node tools/sync-diag.mjs` (each `diag.js` carries its pack's version). `npm run check` fails (`check-versions`, its last step) when a pack's files changed since `origin/master` without a higher version.
- **Performance:** the budget is the whole bundle under 5 ms a tick at 40 players (a scalability check; the Realm itself has at most 10), a typical pack 0.15 ms or less, the heaviest (Minimap, HUDs) 1 ms or less. Perf runs use 10 and 40 players only (never 100 or 5). Profile anything that runs per tick or per player before and after a change (the profiler and `suite.mjs --perf` below, 120 s windows during development; see "Fast testing" in `docs/WORKING.md`), and change performance only when the measurement says so. Releases don't wait for the long soaks or the whole suite: on every PR, CI runs the scenarios it touches and a same-runner perf check (`pr-tests.yml`), and every merge to `master` runs the full validation (`validate.yml`: A/B soaks at 10 and 40, the Realm Bundle at 10 and 40, memory, the whole suite) and files a `perf-report` issue. Fix what it finds on a `perf/<topic>` branch, shipped as a later release ("Testing in CI" in `docs/WORKING.md`). Per-pack perf scenarios (`gear-perf` and the like) run as A/B pairs in CI too: start `validate.yml` on your branch with `scenarios` and `base` instead of queueing them locally. Ship each workstream as its own PR and release.

## Commands

```bash
npm run check 2>&1 | tail -30   # every check (tsc, check-pipeline, ASCII, docs coverage, commands, stories, ids, script events, action bar, unit tests, settings/zones/side/diag/labels copies, catalogs, news, generated packs, versions last); stops at the first failure
npm run test                    # the unit tests alone (tools/**/*.test.mjs)
npm run build 2>&1 | tail -3    # dist/<folder>.mcpack
npm run bundle -- --all         # or --resources; --list [--json]; see the bundle-packs skill. Refreshes the Realm News release first
npm run gen:rain                # or gen:sky, gen:translucent, gen:platypus, gen:build, gen:glyphs: regenerate a resource pack (rain sounds need ffmpeg with libvorbis; their --check in npm run check doesn't)
node tools/help-catalog.mjs     # rebuild /realm:help after docs change (bumps help_bp)
node tools/admin-catalog.mjs    # rebuild the Realm Configuration menu after command changes (then bump admin_bp)
node tools/gen-news.mjs         # copy the newest docs/NEWS.md entry into news_bp (bumps news_bp)
node tools/check-stories.mjs    # validate the story content (ids, flags, every choice path)
node tools/sync-events.mjs      # copy tools/events-shared.js into every pack's script-events.js
node tools/sync-settings.mjs    # copy tools/settings-shared.js into every pack's settings.js
node tools/sync-zones.mjs       # copy tools/zones-shared.js into every safe-zone consumer
node tools/sync-side.mjs        # copy tools/side-shared.js into every pack that writes the side boxes (scripts/side.js)
node tools/sync-diag.mjs        # copy tools/diag-shared.js into every behavior pack (scripts/diag.js, first import of main.js): after EVERY version bump
node tools/sync-labels.mjs      # copy tools/name-labels-shared.js into the four packs with townsfolk name labels
node tools/sync-gossip.mjs      # also sync-prune, sync-weather, sync-spread, sync-owed, sync-spawn, sync-tether: copy tools/<name>-shared.js into the packs that use it
node tools/check-ids.mjs --list # also check-events, check-actionbar: every case, ignoring the allow list (fix a case, remove its line)
node tools/test-bds/setup.mjs   # download BDS once; then:
node tools/test-bds/run.mjs --quiet --only <a_bp,b_bp> --scenario <file>
node tools/test-bds/suite.mjs --filter '<regex>' --retry    # every matching scenario, with the command in its header
node tools/test-bds/suite.mjs --prepare-only              # stage every header recipe offline; no BDS
node tools/test-bds/run.mjs --quiet --flat --bundle dist/realm_bundle.mcpack --scenario tools/test-bds/examples/bundle-smoke.js   # genuine one-context bundle
node tools/test-bds/template-race.mjs --workers 3 --flat   # offline cold-cache race; --real --workers 2 needs native slots
node tools/release.mjs plan                              # inspect ship order; execution needs explicit --execute and receipts
node tools/test-bds/run.mjs --quiet --no-relay --profile --profile-json <out> --only <packs> --scenario tools/test-bds/examples/perf-soak.js --arg players=40 --arg seconds=120 --timeout 3000   # ms/tick per pack
node tools/test-bds/suite.mjs --perf 10,40 [--perf-only a_bp,b_bp]   # the perf soak at 10 and 40 players (120 s each), against the budget; --perf-seconds 300 for release validation
```

Story content lives in `packs/saga_bp/scripts/stories/` and follows `docs/STORY_BIBLE.md` (world, cast, places, data format).
