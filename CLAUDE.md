# mc-packs

Minecraft Bedrock packs for a Realm. Each folder in `packs/` is a self-contained pack: behavior packs `*_bp` (`manifest.json`, `scripts/main.js`, `scripts/config.js`) and six resource packs. `rain_rp`'s textures, fogs, client biomes, sounds and sound definitions are generated by `tools/gen-rain/` (`npm run gen:rain`; its particles and manifest are hand-written). `sky_rp` is generated entirely, manifest included, by `tools/gen-sky/` (`npm run gen:sky`). `translucent_rp` is generated (all but `manifest.json`) by `tools/gen-translucent/` (`npm run gen:translucent`). `hud_rp` (Side HUD) is one hand-written JSON UI file whose vanilla title frames are copied from Mojang's `hud_screen.json`. `platypus_rp`'s model, skins and both platypus pack icons are generated by `tools/gen-platypus/` (`npm run gen:platypus`; its client entity, render controller, animations, lang and manifest are hand-written). `build_rp`'s textures and pack icon are generated by `tools/gen-build/` (`npm run gen:build`; its particles and manifest are hand-written). Never hand-edit generated files.

**Before big or multi-pack work, read `docs/WORKING.md`**: the order of the finishing steps, how subagents and reviewers split the work, known API quirks, and how to keep a session cheap (read `docs/PACKS.md`, 646 KB, one `## ` section at a time; never open generated catalogs).

## Rules

- **Ship every change; don't ask.** The owner has standing approval: never ask whether to open a PR, merge, publish or deploy. Unless the request says otherwise, a change is done only when:
  1. `npm run check` and `npm run build` pass, and the change is committed with its docs, pushed, PR'd to the default branch **`ccr-a6a7a26a-bw0003`** (not `master`) and merged by you with a merge commit (merge the default branch in first if it moved).
  2. In `nishant/hosting` (cloned next to this repo; attach it to a cloud session if it isn't there), `cd minecraft`: `node tools/publish-packs.mjs --from <this repo> --notes "…" --pack-notes <folder>="…"` for every pack whose version went up (`--notes` whenever anything in the Realm Bundle changed), `node tools/pack-docs.mjs --from <this repo>` (and `--check`), `node tools/check-site.mjs realm` (only the realm page changes in a pack publish; a full run is for site changes), then a PR to `main` that you merge (that's the deploy). Docs-only changes skip publishing but still regenerate the realm page.
  3. `node tools/check-live.mjs` there passes: it waits for the deploy and checks the live pages, every pack's latest `.mcpack` and the realm page in Chromium. Never fetch a new file's URL before that: Cloudflare caches a 404.
  4. The owner gets a short summary with numbers, plus the new `.mcpack` files (and the listening clips or pictures when they changed).
- **Review before the first publish**, not after: a publish followed by a fix pass doubles the work.
- **Docs stay current.** Any change to a pack's behavior, commands, config options or saved data updates `docs/PACKS.md` (and the `README.md` pack table if the summary or commands change) **in the same commit**. `npm run check` only checks coverage (every pack, registered command and `config.js` option), so keep descriptions and defaults accurate yourself. Write Commands rows for players: give the default, with the option name in parentheses (`default 64, \`defaultRadius\``).
- **Generated catalogs, regenerated last** (after every doc edit; `npm run check` fails until you do): the in-game `/realm:help` text (`packs/help_bp/scripts/catalog.js`) comes from each pack's summary, `### How to use` and Commands table: `node tools/help-catalog.mjs` (it bumps `help_bp`). The Realm Configuration menu (`packs/admin_bp/scripts/catalog.js`) lists every registered command: after adding or changing a command or its parameters, `node tools/admin-catalog.mjs` and bump `admin_bp`. Nicer labels, ranges and setup checklist entries go in `admin_bp/scripts/presets.js`.
- **The docs are also the players' docs.** `docs/PACKS.md` is published on https://mc.nish.software/realm/ (by `minecraft/tools/pack-docs.mjs` in `nishant/hosting`; see "Publishing to mc.nish.software" in PACKS.md). Every pack section needs a `### How to use` (numbered steps, operators last). Write plain American English (color, gray, behavior, traveled, canceled), but quote in-game text and ids exactly as the code has them, in backticks.
- **New pack:** add `packs/<folder>/` (its `main.js` must answer `/realm:help`: copy the `realm:help_ping` responder from the end of any other pack, with its own folder name), a `## <Name> — \`<folder>\`` section in `docs/PACKS.md` (same layout as the others: what players see, Commands, Configuration, Saved data), a row in the README table, and a mention in "How the packs work together" if it interacts with other packs.
- **Game text is plain ASCII** (plus `§` codes): Bedrock draws `…`, `–`, `•`, `·` or an emoji in a smaller fallback font. Settings are named for what they do with an Enabled/Disabled switch (`invert` for options stored as `off`); never "Turn off ...".
- **Stable APIs only:** `@minecraft/server` 2.1.0 / `@minecraft/server-ui` 2.0.0, no beta modules or experiments, because the packs run on a Realm. Check game ids against `@minecraft/vanilla-data` (see the quirks in `docs/WORKING.md`).
- **Packs stay independent:** no imports between packs. Coordinate through tags, scoreboards or script events (e.g. the AFK pack's `afk` tag that Stats reads). Dynamic property keys use the pack's own prefix (`news:…`). Script event ids are `realm:…` and every message stays under 2048 characters (split long lists into parts, like the safe zones protocol). Before every `setActionBar`, send `realm:actionbar` `{ player, ticks, from }`; a line that redraws every second also listens and waits while someone else's request lasts (the action bar protocol in "How the packs work together").
- **Commands all use the `realm:` namespace**, named `realm:<pack>` or `realm:<pack>_<action>`. A bundle is one add-on and Bedrock allows one command namespace per add-on: a second throws `NamespaceMismatch` and those commands never register.
- **Bundles:** the Realm runs two packs, `npm run bundle -- --all` (Realm Bundle, every behavior pack) and `npm run bundle -- --resources` (Realm Resources, every resource pack), minus those in `tools/standalone.json` (empty). A pack can't mix the two kinds, so two is the minimum; keep it that way. Every pack is still published on its own too. Resource packs are merged only at bundle time, in `dist/`: never merge them on disk (each generator deletes files it didn't make). Standalone and resource packs still follow every rule here so they can join the bundle later.
- **Pictures and sound clips** go in `docs/media/` and a pack's `### See and hear it` subsection (`![caption](media/…)`, `[label](media/….mp3)`, and `![Before](media/…) ![After](media/…) caption` on one line for a before/after pair). The rain packs' are generated (`node tools/gen-rain/renders.mjs`, `node tools/gen-rain/sounds.mjs --audition docs/media/rain`): rerun them when the rain texture, fogs or sounds change. Label renders as renders, never as screenshots.
- **Realm News writes itself:** every shipped change that players notice adds a short entry at the top of `docs/NEWS.md` (for players, plain ASCII). `npm run bundle` runs `node tools/gen-news.mjs`, which puts the newest entry in `news_bp`. Never ask the owner to type news in game.
- **Test on a real server:** `tools/test-bds/` runs the packs on a Bedrock Dedicated Server with simulated players (see its README). Use it for anything that touches game behavior.
- **Vanilla entity overrides:** `translucent_bp/entities/player.json` and `dolphin_bp/entities/dolphin.json` are copies of the vanilla behavior files plus our additions; only one pack may define each entity. After a Minecraft update, re-copy them from the newest vanilla files (BDS ships them) and re-apply the additions.
- **Version bumps:** increase `header.version` in a pack's `manifest.json` whenever its contents change (`sky_rp`: in `tools/gen-sky/gen.mjs`; `help_bp` and `news_bp` are bumped by their generators).

## Commands

```bash
npm run check 2>&1 | tail -30   # every check (tsc, ASCII, docs coverage, commands, stories, settings/zones copies, catalogs, news, generated packs); stops at the first failure
npm run build 2>&1 | tail -3    # dist/<folder>.mcpack
npm run bundle -- --all         # or --resources; --list [--json]; see the bundle-packs skill. Refreshes the Realm News release first
npm run gen:rain                # or gen:sky, gen:translucent, gen:platypus, gen:build: regenerate a resource pack (rain sounds need ffmpeg with libvorbis)
node tools/help-catalog.mjs     # rebuild /realm:help after docs change (bumps help_bp)
node tools/admin-catalog.mjs    # rebuild the Realm Configuration menu after command changes (then bump admin_bp)
node tools/gen-news.mjs         # copy the newest docs/NEWS.md entry into news_bp (bumps news_bp)
node tools/check-stories.mjs    # validate the story content (ids, flags, every choice path)
node tools/sync-settings.mjs    # copy tools/settings-shared.js into every pack's settings.js
node tools/sync-zones.mjs       # copy tools/zones-shared.js into every safe-zone consumer
node tools/sync-side.mjs        # copy tools/side-shared.js into every pack that writes the side boxes (scripts/side.js)
node tools/test-bds/setup.mjs   # download BDS once; then:
node tools/test-bds/run.mjs --quiet --only <a_bp,b_bp> --scenario <file>
```

Story content lives in `packs/saga_bp/scripts/stories/` and follows `docs/STORY_BIBLE.md` (world, cast, places, data format).
